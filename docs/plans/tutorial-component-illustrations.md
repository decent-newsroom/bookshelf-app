# Tutorial component illustrations

Status: implemented, 2026-10-10; owner build/device verification pending. The mapping below records the implementation scope. See [ADR 0059](../decisions/0059-tutorial-component-illustrations.md).

## Implementation results

All 22 steps now select a `TutorialExample`, rendered by the shared frame and reader, social, or search/Settings example composables. Small production controls were extracted or exposed for reuse; editable forms retain their original defaults and use read-only mode in examples. The frame supplies one accessibility description, excludes illustrated controls from keyboard focus, and shields pointer hits without consuming page gestures. Sample passages insert the shared quote through a string placeholder so translations do not independently invalidate highlight offsets.

Static verification passed: main string XML parses without duplicate names, tutorial string references resolve, all 22 unique enum values are assigned, example sources contain no services/effects/modal sheets/independent scroll containers, and scoped tracked-file whitespace checks pass. Catalog unit tests were added but not run. Gradle and device checks remain owner-run under AGENTS.md; no compilation or runtime success is claimed.

## Goal and presentation

Add a focused visual example to each of the existing eight tutorials (22 steps), reusing the app's Compose presentation components with bundled sample data. Preserve topic and step IDs, approved lesson copy, swipe paging, page dots, scroll restoration, close behavior, and final destination actions.

Place the example between the step title and body, where the viewer already supports an optional drawable. Use a consistent rounded frame, a localized “Example” label, and an accessible description. Show one task at a time, with a subtle accent outline around the relevant control where useful. Keep real action labels visible. Avoid screenshots of entire screens, miniature phone frames, and scaled-down text. Examples should reflow at the available width and grow with font size inside the existing page scroll.

Start with non-interactive illustrations. Controls should look like their real counterparts without exposing dead buttons, editable fields, or switches as actionable accessibility targets. Extract shared visual content when necessary so both production controls and illustrative wrappers use the same presentation. Do not obtain this result by disabling everything and turning the illustrations gray. Optional interactive practice can follow separately; it is not required for this plan.

Use a consistent fictional book, short original passage, and deterministic sample chapter/progress data across lessons. Covers must be local or generated by the existing fallback presentation. No remote cover URLs, real account details, or live delivery state. Illustrations follow the current app theme and reader typography; a theme example can use a locally scoped theme without changing app preferences.

## Implementation approach

1. **Add the illustration foundation.** Extend `TutorialStep` with an optional typed component-example identifier, retaining drawable support. Keep the catalog free of composable lambdas and runtime services. Add a composable renderer in `ui/tutorials/` that selects an example and supplies sample models. Define a single illustration source per step and an accessible description resource for each. The frame lives inside the existing scrollable body, without its own scroll container.
2. **Extract the smallest shared presentation pieces.** Begin with navigation, chapter rows, highlighted text, and highlight cards. Prefer existing reusable composables; where interaction is inseparable, extract shared visual content and retain production interaction in the current wrapper. Keep these components in their owning feature packages. Avoid tutorial flags spread through full screens or changes to production behavior merely to support examples.
3. **Implement Start reading and Highlights first.** These six steps establish book, reader-menu, settings, passage, highlight-card, and form examples. Review their on-device size and readability before applying the frame to every topic.
4. **Complete Search, Save and resume, and Read offline.** Reuse the established book/navigation/contents examples and extract search/storage fragments. Do not use full `SearchScreen`, Settings screens, or modal sheets as illustrations.
5. **Complete Reviews, Tracking, and Account.** Reuse form/progress presentation, checking that sample models produce the same labels and visibility rules as the actual app. Include the correct Finish entry point and independent sharing choices.
6. **Document and verify.** Update `docs/tutorials.md`, `docs/ARCHITECTURE.md`, and the decision index with an ADR extending drawable-only illustrations to bundled component examples and recording their no-effects boundary. Add an Unreleased changelog entry when implementation lands. ADR 0059 records the accepted implementation; build/device verification remains pending.

## State and behavior boundaries

Examples receive only local sample models and presentation callbacks. They must not instantiate a ViewModel, repository, connectivity observer, image fetch, signer integration, cache manager, or dispatcher. Construct samples in the tutorial feature, outside production persistence. Opening or swiping a lesson must not fetch data, save a book, create/delete a highlight, enqueue a review, change preferences/progress, or clear a cache. Final-page destination buttons retain their existing behavior and normal destination lifecycle.

Keep sample dates, identifiers, progress values, and private/public states deterministic. Reuse actual progress calculations and visibility rules where appropriate; do not make visually plausible but contradictory state. Existing per-step scroll and pager restoration remain sufficient for the initial illustrative version.

- TalkBack encounters a useful example description without dead action targets or duplicate announcements; decorative emphasis is not the sole explanation. The tutorial's close, paging, and final actions remain accessible.
- Open every topic offline. Confirm there are no remote image requests or other data work and no account, book, cache, outbox, preference, or progress mutations.
- Verify swipe navigation, page dots, body scrolling, rotation restoration, system Back, and final action placement with illustrations present.
- Add focused catalog checks for valid illustration mappings/descriptions and incompatible drawable/component assignments. Add targeted presentation tests where extracting shared code changes important visibility rules; avoid tests that merely restate sample constants.
- Gradle builds/tests and device checks are run by the user under `AGENTS.md`. The agent must not run Gradle verification commands.
